# Founder Build Coach

An AI-powered tool that generates a complete startup build plan for non-technical founders in 60 seconds.

A founder describes their idea, answers 4 clarifying questions, and walks away with a recommended tool stack, a concrete Week 1 sprint plan, and copy-paste prompts for every tool — all generated by a streaming multi-agent AI pipeline.

**Live:** https://v0-founder-build-coach.vercel.app  
**Backend:** https://genesis-founder-coach-production.up.railway.app

---

## What It Does

1. Founder describes their startup idea (minimum 30 characters)
2. Coach calls `/coach/start` — Claude generates 4 tailored clarifying questions
3. Founder answers questions about target user, technical level, budget, and timeline
4. Founder submits — `/coach/plan` streams Server-Sent Events as 4 agents run in sequence:
   - **Agent 1 — Stack Picker:** Recommends the right AI tool for each layer of the MVP
   - **Agent 2 — Sprint Planner:** Generates a concrete, day-by-day Week 1 execution plan
   - **Agent 3 — Prompt Generator:** Writes ready-to-use, copy-paste prompts for each tool
   - **Agent 4 — Eval Judge:** Scores the generated plan across 4 dimensions
5. Frontend renders the full plan with scores, tool cards, sprint accordion, and prompt copy buttons

            Agent 1: Stack Picker      — Claude Sonnet

## Key Engineering Decisions

**Agents are correct here — deliberately.**
In Genesis Portfolio Pulse (my other project), I avoided agents because the pipeline was deterministic. Coach is different — each agent makes a non-deterministic decision based on the previous agent's output. Stack Picker's choices constrain what Sprint Planner can recommend. Sprint Planner's tasks constrain what prompts make sense. That chain of dependent decisions is exactly what agents are for. I use them when the problem demands them, not because they're impressive.

**Streaming SSE — not black-box output.**
The frontend shows each agent's reasoning token by token as it generates, the same way Cursor or Claude Code shows its thinking. Founders see why a tool was recommended, not just the recommendation. This makes the system teachable rather than oracular.

**LLM-as-judge eval layer.**
After all 3 agents run, a 4th Claude call evaluates the generated plan across 4 dimensions: Specificity, Realism, Tool-fit, and Completeness — each scored 1-10 with reasoning. This is the same evaluation pattern I applied in DocPal Finance using RAGAS (0.96 faithfulness score), here applied to generative output instead of retrieval. Plans are scored, not just generated.

**All 4 agents use Claude Sonnet.**
Initial implementation used Groq/Llama 3.3 for agents 1-3 and Claude for eval only. After testing, Llama consistently recommended developer tools to non-technical founders despite explicit rules against it, and hallucinated integrations that don't exist. Claude's instruction-following quality matters more than throughput for a product where plan quality is the entire value proposition. In a production system with higher volume, agents 1-3 would move back to Groq with more extensive prompt engineering.

**Plain Python pipeline, no agent framework.**
No LangChain, no Mastra, no CrewAI. The orchestration is 4 sequential Claude API calls with structured JSON output. Reaching for an agent framework on a sequential pipeline is a junior move. I use Mastra in my own product Videss.ai for more complex multi-agent patterns — the choice of framework depends on the problem, not the other way around.

## Known Limitations

- Input validation is currently length-based (30 char minimum). Semantic validation to catch garbage input is on the roadmap.
- No session persistence — plans are not saved between visits. Session memory with SQLite + RAG is a planned extension.
- No live tool research — recommendations are based on Claude's training knowledge. A planned enhancement would use Firecrawl to fetch current pricing/feature pages before recommending tools.
